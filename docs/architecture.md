# 听荐 AI Demo 技术架构

## 设计目标

听荐不是开放式聊天机器人。它把“用户需求理解、证据检索、程序统计、受约束生成”拆开，确保商品事实、评论数量和引用不由大模型编造。

```text
用户需求
  -> 需求解析（Qwen Flash；无密钥时为本地规则）
  -> 按商品与维度检索评论证据
  -> 程序聚合支持/反对/混合观点
  -> 报告生成（Qwen Plus；失败时为本地模板）
  -> 引用编号校验
  -> 手机端报告、证据页和商品比较
```

## 两条独立状态轴

模型模式与证据来源不能混为一谈。

| 状态轴 | 可选值 | 含义 |
|---|---|---|
| 模型模式 | `local_rules` / `qwen` | 需求解析和报告表达由规则还是千问完成 |
| 证据来源 | `demo_cache` / `derived_dataset` | 证据是合成演示缓存还是真实评论的私有派生数据 |

`GET /api/health` 同时返回 `mode`、`model_configured`、`is_demo_cache` 和 `evidence_source`。前端据此显示“真实评论派生数据 · 本地规则”“真实评论证据 · 千问已连接”或“演示缓存”等准确状态。

### `local_rules`

- 不需要 API Key；
- 用规则解析需求、计算适配方向和生成可追溯模板；
- 可搭配公开合成缓存，也可搭配 D 盘私有真实评论派生证据；
- 规则标注需要人工抽查，不能冒充模型或人工事实判断。

### `qwen`

- 后端从环境变量读取 `DASHSCOPE_API_KEY`；
- 模型负责需求解析与中文表达；
- 统计、阈值、商品字段、评论原文和引用编号仍由程序控制；
- 模型输出中的引用必须能在当前证据集合中找到，否则报告不能直接展示。

## 数据管线

```text
Hugging Face公开文件
  -> 严格HTTP Range候选发现（单次<=2 MiB，总计<=50 MiB）
  -> 人工核验两款同定位耳机
  -> 只保留命中商品，删除用户ID和图片字段
  -> 清洗去重
  -> 六维规则派生证据
  -> FastAPI严格Schema加载
```

服务器不返回 HTTP 206、`Content-Range` 不匹配或响应超过请求长度时，抽样脚本会在读取大响应前停止。范围抽样不具有统计代表性，报告必须保留实际样本量和不足项。

## 数据边界

- 原始 Amazon Reviews 2023 文件、私有商品映射、真实评论派生文件和向量缓存默认存放在 `D:\CodexData\tingjian-ai`，不进入 Git；
- 仓库只公开抽样/清洗/验证代码、数据清单及明确标注的合成演示缓存；
- `verified_purchase` 和 `helpful_votes` 只能辅助排序，不能证明评论真实；
- 对外展示真实短片段前仍需核对数据源最新使用条款；
- 当前私有样本用于端到端验证，不构成购买建议或市场研究结论。

## API

- `GET /api/health`
- `POST /api/needs/parse`
- `POST /api/reports`
- `GET /api/products/{product_id}/evidence`
- `POST /api/compare`

所有请求和响应均使用严格结构；多余字段会被拒绝。API Key 只保存在服务端环境变量中。
